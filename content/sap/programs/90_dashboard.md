## 문제 정의 및 개발 배경
태산자전거 프로젝트에서는 매출, 생산, 재고 정보가 SD, PP, MM 모듈에 나뉘어 있어 경영 현황을 한 화면에서 판단하기 어려웠습니다. 최종 발표에서 정의한 과제 중 하나인 "모바일 기반 협업 및 의사결정 체계 부족"을 해결하기 위한 화면으로 기획했습니다.

매출액만 비교해서는 생산계획 달성 여부나 재고 부담까지 알 수 없습니다. 그래서 매출과 영업이익 같은 금액 지표와 생산 실적, 장기체류 재고 같은 수량 지표를 함께 두고, 요약 현황에서 사업부별 상세 분석까지 이어지도록 설계했습니다.

## 업무 및 데이터 흐름
SD 매출 / PP 생산 / MM 재고 → CDS 데이터 집계 → OData V4 서비스 → SAPUI5 화면 모델 → KPI 카드와 상세 분석 순서로 데이터가 흐릅니다.

### 주요 데이터
| 모듈 | 테이블 | 용도 |
| --- | --- | --- |
| SD | ZTC1SD0012 | 대금청구 기준 매출 |
| PP | ZTC1PP0003 | 생산계획과 실적 수량 |
| MM | ZTC1MM0005 / ZTC1MM0020 | 자재문서와 장기체류 재고 |

### 화면 사용 흐름
- 회사코드, 회계연도, 기준월을 선택하고 조회
- 핵심 경영 현황 카드 4장(총매출, 영업이익률, 생산 달성률, 재고 리스크) 확인
- 카드를 눌러 매출, 재고, 생산 상세 팝업으로 이동
- 하단의 경영 인사이트와 조치 제안, 사업부별 KPI 표 확인
- 두 번째 탭 "사업부 심화 분석"에서 사업부별 매출, 영업이익, 재고 부담 비교
- 필요하면 엑셀 또는 PDF 보고서로 내보내기

## 핵심 구현 내용
### A. CDS 계층 기반 데이터 통합
SD, PP, MM 원천 테이블을 읽는 기반 CDS 위에 사업부와 월 단위로 집계하는 CDS를 쌓고, 서비스 정의에서 화면에 필요한 8개 엔터티를 노출했습니다. 백엔드에서 집계를 끝내 두었기 때문에 화면은 KPI 표현과 사용자 상호작용에 집중할 수 있습니다. 이 서비스는 Behavior Definition 없이 조회 전용으로 구성했습니다.

```abap
define service ZRAP_C1_CO_0018_SRV {
  expose ZCDS_C1_CO_0022 as KpiSummary;
  expose ZCDS_C1_CO_0018 as MonthlySales;
  expose ZCDS_C1_CO_0021 as MonthlyProduction;
  expose ZCDS_C1_CO_0024 as BusinessUnitKpi;
  expose ZCDS_C1_CO_0025 as BusinessUnitProduction;
  expose ZCDS_C1_CO_0026 as BusinessUnitSummary;
  expose ZCDS_C1_CO_0028 as BusinessUnitCost;
  expose ZCDS_C1_CO_0029 as BusinessUnitProfitability;
}
```

### B. OData V4 비동기 병렬 조회
엔터티마다 bindList와 requestContexts로 데이터를 받는 조회 함수를 따로 두고, Promise.all로 여러 조회를 동시에 실행한 뒤 결과를 한 번에 화면 모델에 반영했습니다. 조회하는 동안에는 busy 상태를 표시합니다.

### C. 화면용 데이터 변환 계층
OData 원본을 그대로 쓰지 않고 사업부, 월별 매출, 생산 실적 등 영역별 변환 함수를 거쳐 화면 구조로 바꿨습니다. 금액은 억 단위로, 비율은 양호, 주의, 위험 같은 상태로 바꿉니다.

### D. KPI 시각화와 규칙 기반 인사이트
카드, 차트, 표를 HTML 문자열로 조립해 core:HTML 컨트롤에 넣고, 막대 차트와 도넛 차트는 HTML과 SVG로 직접 그렸습니다. 데이터가 들어가는 부분은 이스케이프 함수를 거칩니다.

| 판정 규칙 | 결과 |
| --- | --- |
| 사업부 생산 달성률 90% 미만 | "생산계획 미달" 인사이트, 오류 상태 |
| 장기체류 평균 일수 365일 이상 | 장기체류 재고 인사이트, 오류 상태 |
| 장기체류 평균 일수 365일 미만 | 장기체류 재고 인사이트, 경고 상태 |

### E. 데이터 소스 전환 구조
OData 응답과 같은 형태의 데이터를 만드는 시연용 데이터 모듈(DemoDataService)을 화면 코드와 분리하고, 컨트롤러의 스위치 함수 하나로 OData 조회와 시연용 데이터를 고르게 했습니다. 시연용 데이터는 무작위 값이 아니라 같은 연, 월, 사업부 조합이면 항상 같은 값이 나오도록 고정 규칙으로 만듭니다.

## 설계 판단 및 트러블슈팅
### 사례 1. 사업부별 재고 데이터 매핑의 한계
- 문제: 매출과 생산은 사업부 단위로 집계할 수 있었지만, MM 자재문서와 장기체류 재고에는 사업부 구분 정보가 없어 사업부별 재고 위험을 서비스에서 만들 수 없었음
- 영향: 화면은 재고 요약 데이터를 부르도록 설계했지만 서비스에 해당 엔터티를 노출하지 못해, 그대로는 재고 카드와 재고 상세 팝업이 비게 됨
- 대응: OData 응답과 같은 구조의 시연용 데이터 모듈을 분리하고 스위치로 전환하게 해 화면 기능을 완성하고 시연함
- 남은 과제: 사업부별 재고 매핑 기준을 정하고 재고 CDS를 만든 뒤, 스위치를 실제 OData 조회로 전환

### 사례 2. 여러 화면에 흩어진 경영지표
- 문제: 초기 버전은 요약, 수익성, 기간 분석, 부서 KPI, 사업부 분석이 각각 다른 화면이라 한 번에 판단하기 어려움
- 해결: 메인 KPI 화면에 매출, 재고, 생산, 인사이트를 모으고, 세부 내용은 상세 팝업으로, 사업부 비교는 두 번째 탭으로 정리
- 해결: 숫자 옆에 양호, 주의, 위험 판정과 조치 제안을 붙여 해석 부담을 줄임

## 검증 및 결과
### 화면 자료의 성격
이 페이지의 화면 캡처는 최종 시연 화면입니다. 최종 시연 버전은 데이터 소스 스위치가 시연용 데이터로 설정되어 있었으므로, 캡처의 매출, 생산, 재고 수치와 사업부 이름은 실제 백엔드 조회 결과가 아니라 시연용 데이터입니다.

### 구현 범위 구분
| 구분 | 내용 | 비고 |
| --- | --- | --- |
| 백엔드 | 매출, 생산, 사업부 집계 CDS와 OData V4 서비스(8개 엔터티) | 서비스 정의와 바인딩 구성 |
| 화면 조회 경로 | 엔터티별 OData V4 조회 함수와 병렬 조회 | 실제 백엔드 연결 화면 자료는 없음 |
| 시연용 데이터 | 재고 요약을 포함한 화면 전체 수치 | 최종 시연에 사용 |
| 화면 기능 | KPI 카드 4장, 상세 팝업 3종, 인사이트, 사업부 KPI 표, 사업부 심화 분석 탭, 엑셀과 PDF 내보내기 | 시연용 데이터로 동작 확인 |

### 배운 점
> KPI의 품질은 화면이 아니라 마스터 데이터와 집계 기준에서 정해진다는 것을 배웠습니다. 매출과 생산은 사업부 기준이 있어 바로 묶을 수 있었지만, 재고는 사업부 매핑이 없어 지표를 만들 수 없었습니다. 준비되지 않은 데이터는 숨기지 않고 별도 모듈과 스위치로 분리해, 백엔드가 준비되면 화면을 고치지 않고 전환할 수 있게 했습니다.
